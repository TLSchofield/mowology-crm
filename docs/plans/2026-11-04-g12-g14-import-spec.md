# G12–G14: QuickBooks import — buildings, billing addresses, shared addresses (build spec, 2026-11-04)

Tim: "Go" (G12–G14 from `2026-11-04-claudia-quickbooks-sending-plan.md`). One change to the import in
`app/Modules/QuickBooks/Services/QboOnboardingService.php` (preview `clients()` + `applyClients()`), one new method in
`ContactService`, one small change to `QboSyncService::ensureCustomer()`. MySQL 5.7, no new tables, no migration.

## Facts read (2026-11-04, this session)

- `applyClients()` imports top-level customers through `ContactService::createContact()` with `property_address`.
  `createContact()` → `attachPropertyToNewContact()` reuses ANY property with the same `address` string and only fills
  its `site_contact_id` if empty → a second client at the same street gets no property of their own (G14). It also
  hardcodes province 'BC'.
- Sub-customers (`ParentRef`) become properties of the parent's contact via `addPropertyToContact()` (same global
  address reuse), and only when they have a `ShipAddr` — a sub-customer with only a `BillAddr` is dropped silently.
- A person's QuickBooks `BillAddr` is passed as `billing_*` to `createContact()`, which stores billing only on a
  `companies` row (`link_company`) → a person with no company loses their mailing address (G13).
- The clients spine (`clients`, migration 1047) has `billing_address/city/province/postal_code/email/phone`,
  `client_type` ('individual' …), `legacy_contact_id` (UNIQUE per `site_id`). No app code inserts `clients` rows today;
  `linkImportedCustomer()` already looks rows up by `legacy_contact_id` / `contact_id`.
- `properties` has `billing_entity_name`, `property_manager_id`, `billing_company_id`, `company_id`.
  `BillToResolver::composeBillToName()` renders "Entity C/O Company" when the property has a billing entity and the
  contact has a company.
- `QboSyncService::ensureCustomer()` picks the QuickBooks customer from `qbo_links` type 'client' keyed by
  `customerOf($inv)[0]` (client → contact → company → billto → property). Import links only contact/company/client keys.
- QuickBooks Customer fields used: `Id`, `ParentRef.value`, `Job` (bool), `BillWithParent` (bool), `DisplayName`,
  `CompanyName`, `GivenName`, `FamilyName`, `PrimaryEmailAddr.Address`, `BillAddr`, `ShipAddr`, `Active`.

## G14 — a second client at the same address gets their own property

1. New `ContactService::addOwnPropertyToContact(int $contactId, array $addr): array` (same return shape as
   `addPropertyToContact`: `['property_id' => int, 'created' => bool]`). Keys: address, city, province (default 'BC'
   only when empty), postal_code, property_name (default the address).
   - Reuse a property at the same address (case-insensitive, trimmed) ONLY when its `site_contact_id` is this contact
     or NULL (fill NULL with this contact). Otherwise INSERT a new property for this contact.
   - Do not change `addPropertyToContact()` or `attachPropertyToNewContact()` (other callers rely on them).
2. `applyClients()`: call `createContact()` WITHOUT `property_address` (empty), then
   `addOwnPropertyToContact($id, $ship + ['property_name' => <display name> . ' Property'])` when there is a street.
   Province now comes from QuickBooks.
3. Matched (already-in-Ittai) customers are unchanged.
4. Preview `clients()`: count street addresses (normalised with `self::norm`) across active top-level customers; when
   two or more DIFFERENT customers share one, each of those rows gets `shared => 'N clients at <address>'` and the
   result gets `shared_addresses` = list of `['address' => ..., 'count' => N]`. `computePreviews()`'s clients line
   appends ", N shared addresses" when any.

## G13 — a person's billing address is kept

In `applyClients()`, for a NEWLY created contact with NO company (`companyOf($c) === null`), when `BillAddr` has a street
and differs from the property street (`norm` compare of address + postal code), write a `clients` row:
`site_id` = `$this->siteId`, `client_type` 'individual', `display_name` = "First Last" (else DisplayName),
`billing_address/city/province/postal_code` from BillAddr, `billing_email` = email or NULL, `billing_phone` = phone or
NULL, `payment_terms` as the contact, `legacy_contact_id` = contact id.
- Idempotent: `INSERT … ON DUPLICATE KEY UPDATE` that only fills billing columns that are NULL/'' (never overwrites).
- Wrapped in try/catch (a schema without `clients` must not stop the import); a failure is counted and named in the
  message ("1 billing address not kept: <reason>").
- Done BEFORE `linkImportedCustomer()` so the new client key gets its QuickBooks link too.
- Matched contacts: same rule, only when no `clients` row exists for them yet (fill blanks only).
- Message adds ", N billing addresses kept".

Known limit (say it, don't fix here): invoice PDFs still print the property address as the bill-to; reading
`clients.billing_*` there belongs to the client/account model's later phase.

## G12 — buildings under a management company (sub-customers)

For each active sub-customer whose parent was imported or matched:

1. Address: `ShipAddr`, else `BillAddr`. No street at all → not imported, counted and named ("<name>: no address").
2. Property via `addOwnPropertyToContact($parentContactId, …)` with `property_name` = the sub-customer's DisplayName
   with a leading "<parent DisplayName>:" / " - " prefix removed when present.
3. `properties.billing_entity_name` = that same name, only when empty (so the invoice header reads
   "<Building> C/O <Parent company>" through `BillToResolver`).
4. Link: `QboLinkService::save(…, 'client', 'property:<property_id>', <sub-customer Id>, null, 'imported', 'sent', null,
   'sub-customer linked at import', $now, true)` (conflict counted like the others). Only when a connection exists
   (same guard as `linkImportedCustomer`).
5. `BillWithParent === false` AND the sub-customer has its own email different from the parent's: do NOT create or
   reroute anyone. Add the row to the result's `own_billing` list (name, email) and the message says
   "N buildings billed on their own — check who gets their invoices". The preview row's `why` says the same.

Sending (`QboSyncService::ensureCustomer`): before the existing lookup, when `$inv['property_id']` is set and a link
'client' / 'property:<property_id>' with a qbo_id exists, use that QuickBooks customer. Nothing else changes; only
imports write such links, so Mowology's own sending is unaffected. In QuickBooks, "Bill with parent" then rolls the
building's invoice up to the parent's statement.

Grouping (preview only, no writes): top-level customers whose DisplayName shares a prefix before " - ", " – ", ":" or
" / " with at least one other top-level customer, prefix ≥ 3 chars after `norm` → result `groups` =
`[['prefix' => 'VML', 'names' => [...]]]`, and each row `group_hint` = prefix. The preview line appends
", N possible building groups". Never merged automatically (Tim: "ask to group, never guess"); the grouping action is a
later step.
