──────────────────────────────────────────────────────────────────────────────
SERVER CONTRACTS
──────────────────────────────────────────────────────────────────────────────
(1) `POST /api/auth/signup.php` (anonymous — `DayApi.anonymousPost`)
    body `{full_name, mobile, email, password, audience:"mobile"}`
    → 200 `{ok:true, sent:["email"] | ["email","sms"], expires_in:900}` (on the local test site also `code` — ignore it; never show it)
    → 400 `{ok:false, error:"validation", fields:{full_name?, mobile?, email?, password?}}` — one message per failing field, shown under that field
    → 409 `{ok:false, error:"taken"}` → "This business already has an owner login — sign in instead." with a link to Sign in
    → 404 `{ok:false, error:"not_available"}` → hide sign-up; show the sign-in screen only
    → 429 `{ok:false, error:"rate_limited"}` → `NativeAuthLogic.SignInError.RATE_LIMITED.message`
    → 502 `{ok:false, error:"send_failed"}` → "The code could not be sent. Try again in a minute."
    Server-side rules the phone mirrors BEFORE sending (same messages, so the two never disagree):
      full_name 2–80 chars after trim AND contains a space → "Enter your full name."
      mobile: 10 digits after stripping everything that is not a digit (an 11-digit number starting with 1 drops the 1) → "Enter your mobile number (10 digits)."
      email: has an @ with something before it and a dot after → "Enter a valid email address."
      password ≥ 10 chars → "Use at least 10 characters."
      confirm == password → "Passwords must match." (phone only)
(2) `POST /api/auth/signup-confirm.php` (anonymous)
    body `{email, code, full_name, mobile, password, audience:"mobile"}` — the sign-up fields are sent AGAIN (the server stores nothing sensitive before the claim), so the view model keeps them in memory until this succeeds, then clears password/confirm.
    → 201 `{ok:true, token, user:{id,email,name,role}, expires_in, business:{key,host,name}, onboarding:{next}}`
       Store the token EXACTLY as sign-in does: `NativeAuthSession.acceptTokenResponse(app, json)` (it is the single session writer). Then open onboarding at `onboarding.next`; `next` null/blank → the Today screen.
    → 400 `{ok:false, error:"code_wrong", message}` / `{error:"code_expired", message}` → show `message` as given, under the code field; code_expired also enables "Send a new code" prominently.
    → 400 validation / 404 / 409 / 429 as in (1). 6-digit check on the phone first: "Enter the 6-digit code."
(3) `GET /api/onboarding/map.php` (JWT, admin — the existing `OnboardingViewModel.MAP_PATH`)
    → `{ok, steps:[{key, title, state, head, skippable, data}], next, ready_to_finish}`; `data` is the per-step object in (5).
    `POST /api/onboarding/map.php {key, do:"skip"|"unskip"}` as today.
(4) `POST /api/onboarding/step.php` (JWT, admin) body `{key, do, …fields}`
    → 200 `{ok:true, next, message?, data?}` (`data` = that step's object after the change)
    → 400 `{ok:false, error:"validation"|"refused", message}` → show `message` inline on the step
    Rows:
      name/save {first, last, preferred} · name/reach {channel: "text"|"email"|"call", mobile} · name/quiet {from "HH:MM", to "HH:MM", weekends: bool}
      company/search {name} → data.matches[{name, registration_number, status, record_id}] · company/confirm {record_id} · company/manual {name}
      quickbooks/yes · quickbooks/no (→ next = books) · quickbooks/read · quickbooks/accept {part}
      books/ack · accountant/invite {name, email} → data.invite {link, expires_at, name} · any skippable key/skip · done/finish
(5) Per-step `data`:
      name: `{first, last, preferred, mobile, channel, quiet:{from,to,weekends}|null, parts:{name:bool, reach:bool, quiet:bool}, next_part}`
      company: `{entered_name, legal_name, operating_name, registration_number, status, confirmed:bool}`
      quickbooks: `{answer:"yes"|"no"|null, connected:bool, has_snapshot:bool, parts:[{key,label,done,summary}], can_write:bool}`
      books: `{acknowledged:bool}` · accountant: `{invited_name|null, logins:int}` · done: `{ready:bool, complete:bool}`
(6) `GET /api/onboarding/quickbooks-start.php` (JWT, admin) → 200 `{ok:true, url}` (an `https://appcenter.intuit.com/...` address) · 409 `{ok:false, error:"not_set_up", message}` → show `message`.
    The phone opens `url` in the phone's browser as a Custom Tab (see C below). When the app resumes, re-read the map; `quickbooks.data.connected` turns true when Intuit finished.
