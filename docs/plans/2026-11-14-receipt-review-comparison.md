# Receipt review sheet: Current vs Penny's suggestion (plan, 2026-11-14)

Tim's brief (three screenshots of the live sheet: top, Penny's read with "Use Penny's version / Keep mine", and the line items): make the review sheet a two-column comparison in the language of the bank-match card (centre divider, restrained borders, rounded container), with "Keep current" / "Apply Penny's changes" under the columns and a fixed "Approve receipt" bar. Scope: the receipt review sheet only; bottom bar, capture, product linking and accounting untouched.

## What exists today (read 2026-11-14)
- `Features/Receipts/ReceiptDetailView.swift`: `pennyReadSection` (~line 187) already shows Penny's read: per field `PennyReadField` (label, penny value, receipt value, reason, confidence "low"/other), `PennyReadItems` (her items vs the receipt's items, each **name + amount only**, with sums), notes, and two buttons "Use Penny's version" / "Keep mine". Line items sit in their own section with Link product, rename, swipe to remove/unlink, Add missed item, Rescan.
- **"Use Penny's version" is not a draft.** `decidePennyRead` posts `mode=penny_apply` / `penny_keep` to the bookkeeper action endpoint; the server (`PennyReadService::rights`) decides who may do which and **whether applying also approves** (`r.approved == true` → the sheet dismisses). Applying replaces the items and teaches the receipt reader the store's layout. So today it persists at once and may approve.

## Gaps against the brief (each needs a decision)
1. **"Must not approve or post automatically" and "draft only, previous version recoverable"** need server work: an apply that stays a draft (no approval, no reader learning until Approve), the original kept with an audit row, and a restore path. Today's apply approves when the server's rights say so. Backend dependency, not faked in the app.
2. **Fields the comparison can show:** Penny's data is label/value pairs plus items with name and amount. Quantity, unit price, SKU, taxes, category and business purpose appear only if the server returns them as fields; items have no quantity/unit price/SKU in `PennyReadItem`. The first job extends the response (or confirms which fields exist) before the UI promises those rows. Rows with no Penny value show "Not proposed", rows missing on the receipt show "Missing" (different from "Unchanged").
3. **Manual edits after choosing:** selection state must be derived (current draft equals Penny's proposal? then "Penny's changes applied"), not stored, so editing flips it honestly.
4. **Her reasoning:** per-field `reason` exists; longer text goes behind an expand control; extraction/learning details behind one optional disclosure that only describes what the server really does (reader learns the store's layout on apply).

## Steps (after the shared header and Receipts list jobs; all three touch `Features/Receipts`)
1. Server (web-builder or Codex web build): draft-apply, keep-original + audit, restore; `PennyReadService` returns the extra comparable fields; tests.
2. iPhone (Codex iOS build): pure `ReceiptComparison` logic (row alignment, changed/unchanged/missing/not-proposed, selection derived from the draft) with tests in `ios/LogicTests`; the two-column container (`HeadSpine`/bank-card metrics reused, no new line component); stack Current over Penny's inside each field at accessibility text sizes / narrow widths; Penny's portrait + short recommendation; compact summary (merchant, date, total, status); expandable photo; fixed bottom "Approve receipt" approving the displayed version; Reject unchanged with its consequence stated.
3. DEBUG demo flag `-mwReceiptCompareDemo` with synthetic cases: many items, long receipt, missing values, no differences, large text, switch versions; screenshots; typecheck, LogicTests, simulator build.
4. Android and web parity as separate jobs.

## Questions for Tim
1. OK to change the server so "Apply Penny's changes" is a **draft** (never approves), with the original kept so it can be restored? Today apply may approve and teaches the reader at once.
2. Which fields must be in the comparison on day one? Penny's data today covers items (name, amount), totals/category fields the server already compares; quantity, unit price, SKU and tax rows need the server change above.

## Decision 2026-11-14 (Tim: "Then forget the draft part")
No server change. "Apply Penny's changes" keeps today's behaviour (`penny_apply`: saves at once, replaces the items, teaches the reader, and the server may approve per `PennyReadService::rights`); "Keep current" is today's `penny_keep`. The sheet states this honestly: the existing `applyNote` stays under the buttons, and the label after applying is the truthful "Penny's changes applied" (plus "Awaiting approval" only when the server has not approved). Dropped from the brief: draft-only apply, keeping the original for restore, no auto-approve. The fixed bottom bar "Approve receipt" approves the receipt as it now stands. Day-one comparison rows = exactly what the server already returns: the fields in `PennyReadField` (label, Penny, receipt, reason, confidence) and items (name, amount, sums); no quantity/unit price/SKU/tax rows until the server sends them. This makes the whole job iPhone UI only: Codex iOS build after the header and Receipts list jobs; no server step, so Steps 1 and the two questions above fall away.
