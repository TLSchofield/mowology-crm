## 3. Storage
- Page inventory text: ~20–50 KB/page × 200 pages ≈ 4–10 MB/tenant (bodies pruned after 90 days → smaller).
- Photo metadata only (originals stay in the existing media system); previews/variants already generated by the media system. Net new ≈ a few MB/tenant/month.
- Ledger/audit rows: <1 MB/tenant/month.

## 4. Hosting and background processing
Production is cPanel shared hosting with cron (confirmed by CLAUDE.md/DEPLOYMENT notes). Assumptions: crawl + audit + scoring run at off-peak, serialised under `CronLock`; a 200-page crawl at 1 req/s ≈ 3–4 minutes of wall time per tenant.
- 10 tenants: serial weekly crawls ≈ 40 min total – fine on current hosting.
- 100 tenants: ≈ 6–7 h of crawl wall time per week, plus drain jobs – still serialisable, but PHP max-execution and shared-host CPU limits become the constraint; needs a dedicated worker host (VPS) or sharded cron.
- 1,000 tenants: ≈ 65 h/week serial → requires parallel workers, a real job queue, and per-tenant database isolation (see Ittai backlog); shared hosting is **not** viable. Cost of a modest VPS fleet is the main infra line.

## 6. Operational cost risks
1. Unbounded loops (retries, tool-use) → mitigated by caps and no free-roaming agent.
2. Re-processing unchanged pages → conditional GET + content hash.
3. Vision on every photo → deterministic pre-filter, shortlist only, existing daily cap.
4. Google API approval delays (GBP) → can't be forecast.
5. Per-tenant cap exhaustion → degrade to deterministic output with "explanation unavailable".
