# Receipts — Offline Upload Pipeline

How receipts move from the field crew's camera into `media_assets` + `expenses`,
including the offline queue, retry logic, and idempotency story.

## Components

| Layer            | File                                                          | Purpose                                                                                  |
|------------------|---------------------------------------------------------------|------------------------------------------------------------------------------------------|
| Capture UI       | `public/crm/expenses_appstack.php`                            | Camera/gallery input, banner, calls `OfflineReceipts.queue` when offline or always       |
| Foreground queue | `public/crm/js/offline-receipts.js`                           | IDB v2 store `pending-receipts`, retry/backoff, status tracking, failed-uploads UI       |
| Background sync  | `public/service-worker.js` (`syncPendingReceipts`)            | Same retry logic as foreground; fires on `sync` tag `receipt-upload` when SW wakes up    |
| Server intake    | `app/Modules/Expenses/Api/receipt-intake.php`                 | Auth, optional CSRF skip, rate limit, dedup by sha256, OCR pipeline, returns `media_id`  |
| Public shim      | `public/crm/api/receipt-intake.php`                           | Forwards to the `/app/` endpoint                                                         |

## IDB schema (v2)

Database: `mowology-receipts`, store: `pending-receipts` (keyPath `id` autoIncrement).

| Field            | Type    | Description                                                                              |
|------------------|---------|------------------------------------------------------------------------------------------|
| `id`             | number  | Auto-increment primary key                                                               |
| `blob`           | Blob    | The captured image                                                                       |
| `lat` / `lng`    | number  | GPS coordinates at capture, optional                                                     |
| `csrf`           | string  | CSRF token at capture; may go stale before sync                                          |
| `idempotencyKey` | string  | UUID generated at queue time; sent as `Idempotency-Key` header on every retry           |
| `timestamp`      | number  | `Date.now()` at capture                                                                  |
| `attempts`       | number  | Retry count (0 = never tried, max 5)                                                     |
| `lastAttemptAt`  | number  | `Date.now()` of the last try                                                             |
| `nextAttemptAt`  | number  | Earliest `Date.now()` for the next try (exponential backoff)                             |
| `status`         | string  | `pending` \| `failed_unrecoverable` \| `deadletter`                                      |
| `lastError`      | string  | Last server error message, capped at 500 chars                                           |

The IDB upgrade from v1 → v2 backfills these fields onto any pre-existing v1 records, so an in-flight queue at deploy time is preserved.

### Status semantics

- **`pending`** — eligible for retry once `nextAttemptAt <= Date.now()`. Counted in the banner badge.
- **`failed_unrecoverable`** — server returned a 4xx (excluding 408 and 429) that won't be fixed by retrying (corrupt file, missing media asset, etc). Surfaced to the user in the failed-uploads chip; user can review and delete.
- **`deadletter`** — exhausted `MAX_ATTEMPTS = 5` retries on transient errors (5xx, 408, 429, network). Same UI surface as `failed_unrecoverable`.

### Retry / backoff

Exponential backoff capped at 1 hour:

| Attempts | Wait before next try |
|----------|----------------------|
| 1        | 2s                   |
| 2        | 4s                   |
| 3        | 8s                   |
| 4        | 16s                  |
| 5        | → deadletter         |

## Idempotency contract

The client generates a UUID per queued record (`idempotencyKey`) and sends it as both:

- `Idempotency-Key` HTTP header (preferred, server-canonical)
- `idempotency_key` POST field (defense in depth in case the header is stripped)

The server treats the **`Idempotency-Key` header** as the authoritative source. When present *and* the request passes `requireLogin()`, the server **skips the CSRF check**.

Why this is safe:

- `requireLogin()` already requires a valid session cookie — a cross-site attacker can't establish that.
- CSRF protects against cross-site form submission. An idempotency key generated by our own JS in an authenticated session is not a CSRF risk.
- The session cookie is `httponly` + `samesite=Lax`, so cross-site fetches don't carry it anyway.

This solves the stale-CSRF problem: a token generated at receipt-capture time may be invalid by the time the SW retries hours later (session rotation), but the idempotency-key path still drains the queue.

The receipt-intake endpoint does **not** currently cache responses by idempotency key (unlike `timer.php` / `job-timer.php`). It relies on the existing **sha256 dedup on `media_assets`** to short-circuit duplicate image uploads — which is the same content-addressed mechanism Phase 1 introduced.

## Server response shape

Success (new image):
```json
{ "success": true, "media_id": 1234, "file_path": "...", "ocr_text": "...", "duplicate_image": null, ... }
```

Success (duplicate, sha256 matched an existing row):
```json
{ "success": true, "media_id": 1234, "duplicate_image": { "existing_media_id": 999, "existing_file_path": "..." }, ... }
```

The client treats either `media_id` or `duplicate_image.existing_media_id` as a successful drain — the record is removed from IDB.

## Outcome matrix (client side)

| HTTP status               | json.success / body                | IDB action                                                        |
|---------------------------|------------------------------------|-------------------------------------------------------------------|
| 2xx                       | `success:true` + `media_id`        | Delete record (drained)                                           |
| 2xx                       | `success:true` + `duplicate_image` | Delete record (drained — server already had it)                   |
| 2xx                       | other                              | Treat as transient — `attempts++`, backoff                        |
| 408, 429, 5xx             | any                                | Transient — `attempts++`, backoff; → `deadletter` at attempt 5    |
| 400, 401, 403, 404, 422   | any                                | `failed_unrecoverable` — surface to user, no further retries      |
| network / abort           | —                                  | Transient                                                         |

## UI surfaces

- **Banner** (`#mw-offline-banner`) on `expenses_appstack.php` shows pending count + "Retry" button.
- **Failed chip** (`#mw-offline-failed-chip`, generated dynamically) appears inside the banner with `"<n> failed"` when any record is `failed_unrecoverable` or `deadletter`. Tapping opens a modal listing each failed record with timestamp, attempt count, last error, and a Delete button. The chip + modal are owned by `offline-receipts.js`.

## Public API (`window.OfflineReceipts`)

| Method                          | Use                                                            |
|---------------------------------|----------------------------------------------------------------|
| `init()`                        | Open IDB, attach online/offline listeners                      |
| `queue(file, lat, lng, csrf)`   | Add a receipt to the queue                                     |
| `remove(id)`                    | Delete a queued record by id                                   |
| `getPendingCount()`             | Count of `status === 'pending'`                                |
| `getFailedCount()`              | Count of `failed_unrecoverable + deadletter`                   |
| `listAll()`                     | All records, for the failed-uploads modal                      |
| `syncNow()`                     | Manually trigger a drain pass                                  |
| `updatePendingBadge()`          | Re-render the banner / counts                                  |
| `showFailedDetail()`            | Open the failed-uploads modal                                  |

## Testing the acceptance scenarios

1. **Stale CSRF survives** — rotate the session token mid-queue (e.g. log out + back in on another tab, or just expire the CSRF cookie). The SW retry should still drain the queue because the `Idempotency-Key` path bypasses CSRF.
2. **422 marks unrecoverable** — return a `422` from `receipt-intake.php` for one record; verify it lands in the failed-uploads chip while other records continue draining.
3. **Repeated 503 → deadletter** — return `503` five times in a row; verify `attempts` increments, `nextAttemptAt` doubles each time, and the record flips to `deadletter` at attempt 5.
4. **Clean 200** — happy path; verify `media_id` returned and the record is deleted from IDB.
